# Data: synthetic claims

All data in this project is **synthetic**, generated by `ml/generate_data.py`. No real person or company data is used. Results on it show that the pipeline works; they are **not** real-world business performance.

```
python ml/generate_data.py --seed 42      # same seed → byte-identical files
```

| File | Contents | Used for |
|---|---|---|
| `data/claims.csv` | Claims and the historical review outcome (the label) | Training, evaluation, the app |
| `data/claims_truth.csv` | Generator-only truth: planted anomalies, hidden risk probability | **Evaluation only.** Never a model feature |

Both files are git-ignored; they're rebuilt from the script.

## Time window

- Claims from **1 Nov 2023 to 31 Oct 2026** (three years, ~30,000 claims, ~7,800 customers).
- The **first year is history only** (`MODEL_START = 2024-11-01`): models are trained and tested on claims from 1 Nov 2024 (~20,000 claims), but features may look back into the first year.
- Why: EDA on a first two-year version showed the review rate rising from 7.8% to 14.7% over time. The cause was the data starting at day one, so customers seemed to have no history early on. Real companies have years of history; the warm-up year reproduces that.

## The label: `manual_review_required`

**Definition:** 1 = this claim needed a manual review; 0 = it didn't. It is **not** a fraud label, and the app must never call it one.

How the generator creates it (documented so results can be interpreted):

1. A hidden risk score adds up several factors: amount vs category median (log), a previous claim within 60 days, the number of claims in the last year, few supporting documents, a policy younger than 90 days, a small category effect, planted anomalies, and **random noise the model never sees**.
2. The score becomes a probability (logistic function), with an intercept chosen so about 12% of claims are positive overall.
3. The label is **drawn** from that probability. Two identical claims can get different labels, so no model can (or should) reach 100%.

Known limitation: a model can only learn the generator's assumptions. A deterministic rule-based label was deliberately avoided, because a model would just rediscover the rule.

## Columns and leakage decisions

| Column | Example | Known at prediction time? | Model use |
|---|---|---|---|
| `claim_id` | CLM-000123 | Yes | **Excluded**: identifier |
| `customer_id` | CUS-00042 | Yes | **Excluded**: identifier; used only to build history features |
| `region` | south | Yes | **Excluded** from features; used only for fairness checks |
| `policy_start_date` | 2024-03-14 | Yes | Only via `policy_age_days` |
| `claim_date` | 2025-06-02 | Yes | Only for the time split and point-in-time features |
| `claim_category` | vehicle | Yes | Feature (one-hot) |
| `claim_amount` | 4200.00 | Yes | Feature |
| `document_count` | 3 (3% missing) | Yes | Feature (missing kept as a signal) |
| `manual_review_required` | 1 | **No**, it's the outcome | **Target** |
| `is_planted_anomaly`, `anomaly_kind`, `hidden_risk_probability` | in `claims_truth.csv` | **No**, generator truth | **Never a feature**; anomaly-detector evaluation only |

Engineered features (`ml/features.py`), all point-in-time:

| Feature | Rule |
|---|---|
| `claim_history_count` | Same customer's claims in the **365 days before** this claim |
| `days_since_previous_claim` | Days since the customer's previous claim (missing if none) |
| `policy_age_days` | Claim date − policy start date |
| `amount_vs_category_median` | Amount ÷ category median, with medians from **training data only** |

Checks in code: `tests/test_features.py` proves that adding a future claim doesn't change today's features, and that claims older than 365 days don't count.

## EDA findings (training period only)

Full output and charts: [`docs/eda/README.md`](eda/README.md), produced by `python ml/eda.py`.

- **Imbalanced target:** 13.0% positive in the training period → use PR-AUC, precision, recall and class weights, never accuracy.
- **Stable over time** after the warm-up fix: monthly review rate 10.5–14.5%, no trend.
- **Amounts** are log-normal per category (medians: device ~300, travel ~400, health ~1,200, home ~2,500, vehicle ~3,500), so the ratio to the category median is more informative than the raw amount.
- **Signals that exist:** review rate rises with the amount ratio (3.7% below half the median → 44% above 4×), with claims in the last year (7% with none → 25% with 4+), with a previous claim under 60 days ago (23–24% vs 9–12%), and with zero documents (17% vs 11–14%).
- **Missing values:** `document_count` 3%, `region` 1%, `days_since_previous_claim` missing for a customer's first claim (that's meaningful, not an error).
- **Leakage check:** no single feature ranks the label with ROC-AUC above 0.71 (alarm level: 0.9).
- **Fairness check:** review rates by region are within 0.8 percentage points (12.7–13.5%).
